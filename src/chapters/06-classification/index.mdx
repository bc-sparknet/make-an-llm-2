After Chapter 5 you have a GPT that has read a lot of text and can continue a sentence. That's impressive, but "continue this text" is rarely the job you actually need done.

In this chapter we'll give the model a narrow, practical skill: reading a text message and deciding whether it's **spam**. Along the way you'll see how little of the network needs to change to repurpose it.

## Two kinds of fine-tuning

Fine-tuning means continuing to train a pretrained model on a smaller dataset built for a specific job. The two most common flavours are:

- **Classification fine-tuning.** The model learns to pick one label from a fixed set: spam or not spam, positive or negative, one of 20 topics. The output is a label, never free text.
- **Instruction fine-tuning.** The model learns to respond helpfully to requests written in plain language: "Summarise this", "Translate that". The output is free-form text (Chapter 7).

An instruction-tuned model is the more flexible of the two: it can often classify text too, if you ask nicely. So why bother with a dedicated classifier?

<Callout type="key">
Reach for **classification fine-tuning** when the set of answers is fixed and known in advance, you have labelled examples, and you care about speed, cost and reliability. Reach for **instruction fine-tuning** when you need one model to handle many different kinds of request.
</Callout>

A classifier can be small, needs relatively little data, always returns a valid label and is trivial to evaluate: you just count how often it's right.

## Preparing the dataset

We'll use the public **SMS Spam Collection**: about 5,600 real text messages, each labelled `ham` (a normal message) or `spam`. It's a plain tab-separated file, so pandas can load it directly.

```python
import pandas as pd

df = pd.read_csv(
    "sms_spam_collection/SMSSpamCollection.tsv",
    sep="\t", header=None, names=["Label", "Text"],
)
print(df["Label"].value_counts())
# ham     4825
# spam     747
```

### Balancing the classes

Ham outnumbers spam more than six to one. A lazy model could answer "ham" every time and still be 87% accurate, which tells us nothing.

The simplest fix is **undersampling**: keep every spam message and randomly pick the same number of ham messages. We lose some data, but end up with a balanced set where 50% accuracy is the baseline for guessing.

```python
def balance(df, seed=123):
    spam = df[df["Label"] == "spam"]
    ham = df[df["Label"] == "ham"].sample(len(spam), random_state=seed)
    return pd.concat([ham, spam])

balanced = balance(df)
balanced["Label"] = balanced["Label"].map({"ham": 0, "spam": 1})
```

Mapping the labels to `0` and `1` matters later: those integers become the indices of the model's two outputs.

### Train, validation and test splits

Next we shuffle and cut the 1,494 messages into three parts:

- **70% training**: what the model learns from.
- **10% validation**: checked during training to spot overfitting and tune settings.
- **20% test**: touched only once, at the very end, for an honest final score.

```python
def split(df, train_frac=0.7, val_frac=0.1, seed=123):
    df = df.sample(frac=1, random_state=seed).reset_index(drop=True)
    n_train = int(len(df) * train_frac)
    n_val = int(len(df) * val_frac)
    return (
        df[:n_train],
        df[n_train:n_train + n_val],
        df[n_train + n_val:],
    )

train_df, val_df, test_df = split(balanced)
for name, part in [("train", train_df), ("validation", val_df), ("test", test_df)]:
    part.to_csv(f"{name}.csv", index=False)
```

### Padding to a common length

In pretraining we chopped one long text into equal-sized chunks. Here every message is its own example, and messages have wildly different lengths. But a batch has to be a rectangular tensor.

There are two options: cut every message down to the shortest one (losing information), or **pad** every message up to the longest one. We pad, using GPT-2's `<|endoftext|>` token, ID `50256`:

<PaddingDemo />

Wrapping this in a PyTorch `Dataset` keeps the logic in one place. We tokenise everything once, find the longest training message, and pad the rest to match:

```python
import tiktoken
import torch
from torch.utils.data import Dataset

tokenizer = tiktoken.get_encoding("gpt2")
PAD_ID = 50256  # <|endoftext|>

class SpamDataset(Dataset):
    def __init__(self, csv_path, tokenizer, max_length=None):
        self.df = pd.read_csv(csv_path)
        encoded = [tokenizer.encode(t) for t in self.df["Text"]]

        # Use the longest message unless a length is imposed (for val/test)
        self.max_length = max_length or max(len(ids) for ids in encoded)
        self.inputs = []
        for ids in encoded:
            ids = ids[:self.max_length]                      # truncate if too long
            ids += [PAD_ID] * (self.max_length - len(ids))   # pad if too short
            self.inputs.append(ids)

    def __getitem__(self, idx):
        x = torch.tensor(self.inputs[idx])
        y = torch.tensor(self.df.iloc[idx]["Label"])
        return x, y

    def __len__(self):
        return len(self.df)

train_ds = SpamDataset("train.csv", tokenizer)
val_ds = SpamDataset("validation.csv", tokenizer, max_length=train_ds.max_length)
test_ds = SpamDataset("test.csv", tokenizer, max_length=train_ds.max_length)
print(train_ds.max_length)  # 120
```

<Callout type="note">
Validation and test messages are padded (or truncated) to the **training** length. Any length up to the model's 1,024-token context would work, but keeping them consistent is tidy.
</Callout>

Finally, `DataLoader`s serve the data in shuffled batches of 8:

```python
from torch.utils.data import DataLoader

torch.manual_seed(123)
train_loader = DataLoader(train_ds, batch_size=8, shuffle=True, drop_last=True)
val_loader = DataLoader(val_ds, batch_size=8)
test_loader = DataLoader(test_ds, batch_size=8)

x, y = next(iter(train_loader))
print(x.shape, y.shape)  # torch.Size([8, 120]) torch.Size([8])
```

Each batch is 8 messages of 120 token IDs, plus 8 labels. That gives 130 training batches per epoch.

## Adding a classification head

GPT-2's last layer, `out_head`, maps each 768-dimensional token vector to 50,257 scores, one for every token in the vocabulary. For spam detection we need just two scores: "not spam" and "spam".

So we throw the old head away and put a small new one in its place. Toggle between the two below:

<HeadSwapDiagram />

### Freezing most of the network

We *could* fine-tune all 124 million parameters. But the lower layers capture general features of language that are just as useful for spotting spam, and training them on 1,000 messages risks damaging that knowledge.

A good compromise: freeze everything, then unfreeze only the top. In PyTorch, freezing means setting `requires_grad = False`, so the optimizer never updates those tensors.

```python
# 1. Freeze every existing parameter
for p in model.parameters():
    p.requires_grad = False

# 2. Swap in a new head. Fresh layers are trainable by default.
torch.manual_seed(123)
num_classes = 2
model.out_head = torch.nn.Linear(BASE_CONFIG["emb_dim"], num_classes)

# 3. Unfreeze the last transformer block and the final LayerNorm
for p in model.trf_blocks[-1].parameters():
    p.requires_grad = True
for p in model.final_norm.parameters():
    p.requires_grad = True
```

<Callout type="tip">
Unfreezing the last block as well as the head noticeably improves accuracy. Training only the head also works, just not quite as well. It's cheap to experiment with unfreezing more or fewer blocks.
</Callout>

### Which output do we use?

The model still produces one output per input token. Feed it four tokens and you get back a tensor of shape `[1, 4, 2]`: two scores for each of the four positions.

```python
inputs = torch.tensor(tokenizer.encode("Are you free tonight")).unsqueeze(0)
with torch.no_grad():
    outputs = model(inputs)
print(outputs.shape)  # torch.Size([1, 4, 2])
```

But a message gets **one** label, so we need to pick one position. Which one? Remember the causal mask from Chapter 3: each token can only attend to itself and the tokens before it.

<LastTokenDemo />

The first token has seen only itself. The last token is the only one whose output was computed with the whole message in view. So that's the one we train and read:

```python
last_logits = outputs[:, -1, :]
print(last_logits)  # tensor([[ 0.8121, -1.3406]])  (random head, for now)
```

<Callout type="key">
In a decoder-only model, the **last token's output** is a summary of the entire input. Classification uses it and ignores the rest.
</Callout>

## Loss and accuracy

The two numbers in `last_logits` are logits, just like the 50,257 logits in Chapter 5, only fewer. Softmax turns them into probabilities, and the predicted label is whichever is larger. Since softmax preserves order, `argmax` on the raw logits gives the same answer.

```python
probs = torch.softmax(last_logits, dim=-1)
label = torch.argmax(probs, dim=-1)   # same as argmax(last_logits)
```

### Accuracy

Accuracy is what we actually care about: the fraction of messages labelled correctly. This helper computes it over (some batches of) a data loader:

```python
def accuracy(loader, model, device, num_batches=None):
    model.eval()
    correct, seen = 0, 0
    num_batches = min(num_batches or len(loader), len(loader))
    for i, (x, y) in enumerate(loader):
        if i >= num_batches:
            break
        x, y = x.to(device), y.to(device)
        with torch.no_grad():
            preds = model(x)[:, -1, :].argmax(dim=-1)
        correct += (preds == y).sum().item()
        seen += y.shape[0]
    return correct / seen
```

Before any fine-tuning, the new head is random, so accuracy hovers around **50%**: a coin flip, exactly what you'd expect on a balanced dataset.

### Loss

Accuracy can't be optimised directly: it jumps in steps, so it has no useful gradient. Instead we minimise **cross-entropy**, as in pretraining. The only change is that we compute it on the last token's two logits against the true label:

```python
def loss_batch(x, y, model, device):
    x, y = x.to(device), y.to(device)
    logits = model(x)[:, -1, :]            # [batch, 2]
    return torch.nn.functional.cross_entropy(logits, y)

def loss_loader(loader, model, device, num_batches=None):
    num_batches = min(num_batches or len(loader), len(loader))
    total = 0.0
    for i, (x, y) in enumerate(loader):
        if i >= num_batches:
            break
        total += loss_batch(x, y, model, device).item()
    return total / num_batches
```

## Fine-tuning and evaluating

The training loop is almost the same as the one from Chapter 5. We still compute a loss, backpropagate and step the optimizer. The difference is what we track: accuracy after each epoch, and the number of examples seen instead of tokens.

```python
def train_classifier(model, train_loader, val_loader, optimizer, device,
                     num_epochs, eval_freq=50, eval_iter=5):
    step = 0
    for epoch in range(num_epochs):
        model.train()
        for x, y in train_loader:
            optimizer.zero_grad()
            loss = loss_batch(x, y, model, device)
            loss.backward()
            optimizer.step()
            step += 1

            if step % eval_freq == 0:
                model.eval()
                with torch.no_grad():
                    tr = loss_loader(train_loader, model, device, eval_iter)
                    va = loss_loader(val_loader, model, device, eval_iter)
                model.train()
                print(f"epoch {epoch+1} step {step}: train {tr:.3f}, val {va:.3f}")

        tr_acc = accuracy(train_loader, model, device, eval_iter)
        va_acc = accuracy(val_loader, model, device, eval_iter)
        print(f"  accuracy: train {tr_acc:.0%} | val {va_acc:.0%}")

device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model.to(device)
optimizer = torch.optim.AdamW(model.parameters(), lr=5e-5, weight_decay=0.1)
train_classifier(model, train_loader, val_loader, optimizer, device, num_epochs=5)
```

Five epochs take a few minutes on a laptop CPU and well under a minute on a GPU. The loss falls steeply in the first epoch, and training and validation curves stay close together, which is a sign the model isn't just memorising.

<Callout type="note">
Because the frozen parameters have `requires_grad = False`, AdamW simply skips them. Passing all of `model.parameters()` to the optimizer is fine.
</Callout>

### The final score

With training done, we measure accuracy on the full splits, including the test set for the first time:

```python
for name, loader in [("train", train_loader), ("val", val_loader), ("test", test_loader)]:
    print(f"{name}: {accuracy(loader, model, device):.1%}")
```

Around 96% on messages the model has never seen, from roughly 1,000 training examples and a few minutes of training. That's the payoff of starting from pretrained weights. The small gap between validation and test is normal.

### Classifying new messages

To use the classifier, we repeat exactly what the dataset did: tokenise, truncate or pad to the training length, run the model, and read the last token's logits.

```python
def classify(text, model, tokenizer, device, max_length=120):
    model.eval()
    ids = tokenizer.encode(text)[:max_length]
    ids += [PAD_ID] * (max_length - len(ids))
    x = torch.tensor(ids, device=device).unsqueeze(0)
    with torch.no_grad():
        label = model(x)[:, -1, :].argmax(dim=-1).item()
    return "spam" if label == 1 else "not spam"

print(classify("Congratulations! You have won a free cruise. "
               "Reply YES now to claim your prize.", model, tokenizer, device))
# spam
print(classify("Running ten minutes late, can you save me a seat?",
               model, tokenizer, device))
# not spam
```

<Callout type="key">
Classification fine-tuning in three moves: **reuse** a pretrained body, **replace** the output head with one output per class, and **train** on the last token's output with cross-entropy.
</Callout>
